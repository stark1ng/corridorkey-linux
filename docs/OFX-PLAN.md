# Нативный OFX-нод для DaVinci Resolve: честная оценка

Статус: **не начато, только оценка**. Рабочий путь сегодня — `resolve_compose.py`
(сборка композа в Fusion) + `resolve_client.py` (импорт в медиапул).

## Что нужно, чтобы OFX вообще имел смысл

OFX-плагин вызывается хостом **на каждый кадр**: Resolve отдаёт `OFX::Image`
(обычно RGBA float/half), плагин возвращает результат. Внутри процесса Resolve нет
Python, нет torch, нет CUDA-контекста в удобном виде — значит модель должна жить в
отдельном процессе, а плагин обменивается с ним кадрами.

Компоненты:

1. **Плагин (C++/OFX SDK)**: `describe`, `describeInContext`, `render`.
   ~600–900 строк для MVP, без интерактивного UI-парсера параметров.
2. **IPC**: `/dev/shm` POSIX-shared memory на кадр (4K RGBA half = 66 МБ) +
   unix-сокет для команд. Нужен двойной буфер и таймаут.
3. **Бэкенд**: демон (`daemon.py`) уже умеет очередь и инференс, но ему нужен
   режим «один кадр по запросу» вместо «весь клип»: загрузка весов 20–30 с, поэтому
   процесс должен жить между кадрами и держать модель в VRAM.
4. **Хинт первого кадра**: у OFX нет файлового пикера по умолчанию, но есть
   строковые параметры — путь к PNG-маске передаётся параметром нода.
5. **Кэш шота**: без него Resolve пересчитает каждый кадр при каждом скраббинге.
   Ключ = хеш (файл, таймкод, параметры).

## Главный риск: время

* Временной контекст. Модель работает окнами Hann 80/24/8 кадров. OFX-нод по
  умолчанию **без состояния**; чтобы получить соседние кадры, нужен
  `kOfxImageEffectPropTemporalClipAccess` + запрос клипов на диапазон. Resolve это
  поддерживает, но не для всякого типа эффекта и с падением скорости.
* Замеры на этой машине: 1.3 с/кадр на 1080×1920 (окно 24/12), ~6 с/кадр на 4K.
  То есть нод в Resolve — **только для финального рендера**, не для интерактива.
  Это нормально для кеинга, но пользователь должен это понимать заранее.

## Оценка объёма (в фокусных днях)

| Этап | Дни | Комментарий |
|---|---|---|
| OFX SDK + сборка плагина, который грузится в Resolve | 1–2 | CMake + `openfx` (BSD), версия SDK под Resolve 21 |
| passthrough-нод: читает кадр, отдаёт его же | 0.5 | проверка, что хост реально зовёт рендер |
| shared memory + сокет + вежливые таймауты | 2–3 | самый нудный, но предсказуемый кусок |
| бэкенд «один кадр»: переиспользовать `daemon.py` | 2–3 | нужен режим без очереди, с прогревом модели |
| кэш шота, прогресс, обработка ошибок, отмена | 1–2 | без кэша нод бесполезен |
| временной контекст (соседние кадры через OFX) | 3–5 | **главный риск**, может не взлететь в Resolve |
| упаковка, документация, тесты на 4K | 2 | |

**Итого MVP: ~12–18 фокусных дней**, из них 3–5 — рискованный temporal-access.
Полный паритет с текущим приложением (очередь, профили VRAM, превью) — заметно больше.

## Что это даёт и не даёт

* Даёт: нод прямо в нод-графе Fusion/Color, без скриптов и импорта EXR.
* Не даёт: интерактивной скорости; на 16 ГБ VRAM модель и Resolve всё равно
  конкурируют (сейчас это решается тем, что рендер и Resolve не работают вместе).
* Лицензия: результаты — можно коммерчески, сам нод — нельзя продавать и нельзя
  делать платный инференс-сервис (CC BY-NC-SA + доп. условия апстрима).

## Рекомендация

Сначала закрыть текущий путь: `resolve_compose.py` уже собирает композ в Fusion,
`resolve_client.py` импортирует в медиапул. OFX брать в работу только если нужен
именно «нод в графе» для чужих проектов/продажи пайплайна — и начинать с шага
«temporal access»: если Resolve не отдаёт окно кадров, вся затея превращается в
покадровый одиночный режим с плохим качеством маски (модель без контекста).
